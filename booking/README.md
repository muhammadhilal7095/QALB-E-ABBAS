# Qalb-E-Abbas — Online Meeting Booking & Payment System

Clients book a paid online consultation (type → purpose → date/time → details → secure payment → confirmation). The team manages meetings, availability, payments, refunds and reports in an admin dashboard.

Built with Next.js 15 (App Router, TypeScript), PostgreSQL + Prisma, Stripe Checkout, Tailwind CSS.

The static marketing site in the parent folder links here: its header **Book Consultation** button goes to `book-consultation.html`, which forwards each `?topic=` to the matching meeting type (see `links.bookingApp` in `../assets/js/site-config.js`).

## Quick start (local development)

Requirements: Node.js 20+.

```bash
cd booking
npm install
cp .env.example .env          # defaults work for local dev

npm run db:local              # terminal 1 — embedded PostgreSQL on :5433 (keep running)
npm run db:deploy             # create tables (first run)
npm run db:seed               # settings, 10 meeting types, working hours, demo accounts
npm run dev                   # terminal 2 — http://localhost:3000
npm run worker                # terminal 3 (optional) — hold expiry + reminders every minute
```

Already have PostgreSQL? Skip `db:local` and set `DATABASE_URL` / `TEST_DATABASE_URL` to your server.

### Payments in development

With no Stripe keys and `PAYMENT_MOCK_ENABLED="true"`, checkout offers a **test gateway** with *Pay*, *Decline* and *Cancel* buttons. It runs the same fulfilment code as real webhooks. It is switched off automatically when `NODE_ENV=production`.

To test real Stripe (test mode): add `sk_test_…` to `STRIPE_SECRET_KEY`, run `stripe listen --forward-to localhost:3000/api/webhooks/stripe`, copy the printed `whsec_…` into `STRIPE_WEBHOOK_SECRET`, and pay with card `4242 4242 4242 4242`. Use `4000 0000 0000 0002` to see a decline.

### Emails in development

Without `RESEND_API_KEY`, emails are not sent — every message is recorded and viewable in **Admin → Email log**.

## Service shop (cart & orders)

Fixed-price services (account creation, PPC, tax filing, trademarks…) can be bought from the website. Each service page has a **Pricing** section with *Add to cart* buttons; the cart lives at `cart.html` on the website and checks out through this app.

| Concern | Where |
|---|---|
| Prices & services (single source of truth) | `src/lib/service-catalog.json` |
| Pricing sections on the website | generated by `npm run pricing:build` (between `PRICING:START/END` markers) |
| Cart, header count, checkout form | `../assets/js/cart.js`, `../cart.html` |
| Orders, payment, emails | `src/lib/orders.ts`, `src/app/api/orders` |
| Client order page | `/order/[ref]?token=…` |
| Admin | **Admin → Service orders** (mark bank transfers received, start/complete/cancel) |

To change a price: edit `service-catalog.json`, run `npm run pricing:build`, and run `npm test` (a test checks every button on the site matches the catalog). The server always re-prices orders from the catalog, so prices in the browser can't be tampered with. One order = one currency; a cart with USD and GBP services is paid in two checkouts. US LLC / UK LTD plan buttons are hand-written in those pages — keep their `data-price` in step with the catalog (the test will catch a mismatch).

## Tests

```bash
npm test          # needs db:local running; uses the separate qalb_booking_test database
```

25 automated tests cover slot generation, time zones, buffers, the database double-booking constraint, 8 simultaneous bookings for one slot (exactly one wins), hold expiry, idempotent payment fulfilment, amount mismatch, failed/cancelled/late payments, deposits, manual approval, full/partial refunds, and Stripe webhook signature + duplicate handling.

## How it works

| Concern | Where |
|---|---|
| Slot calculation (hours, breaks, overrides, blocks, buffer, notice, daily limit) | `src/lib/availability.ts` |
| Holds, reschedule, status transitions | `src/lib/booking.ts` |
| Server-side pricing (coupon, tax, deposit) | `src/lib/pricing.ts` |
| Checkout, fulfilment, refunds | `src/lib/payments.ts` |
| Stripe webhooks | `src/lib/webhooks.ts`, `src/app/api/webhooks/stripe` |
| Emails & templates | `src/lib/email.ts` |
| Reminders & hold expiry | `src/lib/jobs.ts` (`npm run worker` or `/api/cron`) |
| Auth, sessions, roles | `src/lib/auth.ts`, `src/middleware.ts` |

**No double booking:** a slot is reserved inside a transaction holding a per-date advisory lock, and a PostgreSQL exclusion constraint (`booking_no_overlap`) rejects any overlapping active booking (including buffer time) even if application code is bypassed.

**Payment safety:** the amount is always computed on the server and stored on the booking. A booking is confirmed only from a verified Stripe webhook (or the session check on the return page), fulfilment is idempotent, and card data never touches this server.
